3 · Options

IMU

—
Two stock driver bugs, both fixed here.
1) Zephyr’s LSM6DSV16X driver temporarily sets accel/gyro to the SFLP rate to load the gyro bias, then “restores” a value it has just overwritten, so the configured rate never sticks. Raw modes patch that restore (2 instructions).
2) High-accuracy ODR never turns on. The sensor only runs from the HA table when OP_MODE (CTRL1/CTRL2 bits 6:4) = 001, and HAODR_SEL can only be written while both sensors are off. The stock data-rate setters power the sensor on first and never set OP_MODE, so “HA01 1000 Hz” silently ran at HP 960 (and Valve’s own HA01 250 ran at 240). Gyro 1000 HA rewrites both setters in place (same size): HAODR_SEL first, then CTRL with OP_MODE=HA. Verified on hardware (in sc26re): batch period 1047 → 998 µs, quaternion/SFLP still works.

Measured (stock fw, USB 1000): gyro 960 + stock FIFO = most reports (~917/s) but IMU fields refresh only with accel samples (~480/s). With the IMU fast path + lean FIFO + HA 1000: watermark 2 → 757 reports / 532 fresh gyro; watermark 1 → 640 / 640 (no repeated gyro). The quaternion stays capped at 480 Hz by silicon.
Hz (480 = silicon cap)
Game-rotation vector + gyro-bias rate from the sensor’s fusion block. The accelerometer is kept at 480/500 Hz in raw modes so it never falls below the SFLP rate.
fewer FIFO words = less I²C
The accelerometer keeps running at 480/500 Hz (SFLP needs it), but only every 2nd/4th sample is batched into the FIFO. Fewer words per second means shorter I²C reads and less time with the report loop blocked. Use with the IMU fast path, which reuses the last accel sample for gyro-only batches. Paired with SFLP 120 this is the “lean FIFO” that gave the biggest gain in sc26re.
stock
How many FIFO words collect before the IMU thread wakes. Lower = fresher gyro, more interrupts and I²C reads. Without the fast path anything below 4 stalls the IMU (the stock handler drops incomplete batches and floods the log), so values below 4 are only accepted with the fast path. Measured with fast path + lean FIFO + HA 1000: 2 → 757 reports/s, 532 fresh gyro/s (≈30% of reports repeat a gyro sample); 1 → 640 reports/s, 640 fresh (0% repeats). 3 or more gives fewer fresh samples.
Why IMU stops at ~480/s: the stock handler (0x3ba00) builds one report sample per FIFO batch and drops the whole batch (with a LOG_ERR) unless it contains accel and gyro and gyro-bias and quaternion. The SFLP outputs cap at 480 Hz, so at most ~480 complete batches/s. That's also why watermark 2 or removing gbias killed the IMU: every batch failed and the error log flooded the CPU.

Fast path (5 branch patches + 236 B appended code): a batch only needs gyro. Missing accel or quaternion reuse the last values from the report state; missing gyro bias uses a cache (the driver’s gbias_udps, refreshed from every SFLP bias sample, which is also what the SFLP is re-seeded with on stream restart). Batches without gyro return quietly. Tested stable on hardware with watermark 3, 2 and 1 (see the watermark notes for numbers).
experimental
nRF52833 TWIM documents only up to 400 kHz; 800 writes an undocumented FREQUENCY value. The same bus carries the MP2733 charger. On stock fast path + wtm 3 it gave a small gain (≈663 reports / ≈599 fresh), but in the sc26re builds it made things worse, and 1000 kHz crashed the controller (option removed). Keep 400 unless you are experimenting. Recover via the bootloader and flash a 400 kHz file. experimental

Report rate

—
How stock paces reports: the report thread (ibex_loop) sleeps on a semaphore. Each transport wakes it with a deadline: USB uses a k_timer of 132 ticks (4.03 ms ≈ 248 Hz); the wireless links wake it ~0.5 ms before each radio slot so inputs are sampled just in time.

USB timer changes only that one constant (1 byte). The loop stays event-driven: no busy-spinning, no thread starvation, and the wireless just-in-time timing stays intact. recommended
Free-run is the v1 approach: it replaces the wait with a short timeout and removes the sleep, so the loop runs on every link. Note that the kernel tick is 32768 Hz, not 16384: 16 ticks ≈ 2048 Hz loop, 33 ticks ≈ 993 Hz.
USB full speed polls at 1000 Hz max (the firmware declares bInterval 1). Wireless rate is set by the Puck (n × 1.25 ms), so it needs OpenPuck.
—
Converted to whole ticks (32768 Hz): 1000 Hz → 33 ticks = 993 Hz. Anything above 1000 is wasted on USB (one report per 1 ms frame) and just adds work. 993 Hz means a repeated report roughly every 140 ms, which is harmless.
—
33 ticks ≈ 993 Hz. v1 defaulted to 16–17 because it assumed a 16384 Hz tick, which really spun the loop at ~2 kHz.
Steam reads ATTRIB_CONNECTION_INTERVAL_IN_US (attribute 11) from the controller; stock returns 4000 for USB. This makes it return the patched interval. The same code path also serves one of the Puck link types, so that link would report the USB interval too. Leave off unless you are testing whether Steam uses it.
lower number = higher prio
Static thread priorities in this firmware: IMU / ESB / puck / haptics 9, state machine 10, keyboard / lizard / ibex_loop 8, input 14. At 8 the report thread outranks the IMU and radio threads, so any extra report work runs before them. Under v1 free-run that hung the controller on both cable and wireless. Auto puts it at 14 whenever polling is patched (the value that is known to fix the hangs): IMU, ESB and puck can always preempt it, and it shares time with the input thread. It still wakes every ~1 ms on USB, so report latency is unaffected in practice. Tested: 10 makes the controller reboot every 1–2 s (watchdog), so values between 8 and 14 are not offered.

Sticks & touch

8 = stock
Replaces the adaptive touch-on threshold ([r4+0xac]) with a fixed value at the detection compare; release is 85% of it. 8 = leave stock (the adaptive value is computed at runtime, so “8” is a placeholder, not a measured stock number). Higher = less sensitive (rejects hover). Range 1–65535.
blank = stock
The same per-stick routine has a second capacitive channel with its own hysteresis ([r4+0xc8] on / 0xcc off) and its own touch flag. Its purpose isn’t confirmed yet. Only touch it if you are testing which physical sensor it maps to. experimental
When the capacitive sensor reports no finger, the firmware still flags a touch if the stick deflection magnitude exceeds 12000 (out of ~32767). Off = touch only from the sensor. Custom keeps the feature but moves the threshold: higher = only big deflections count.

Gyro calibration

stock
The SFLP’s embedded gyro-bias calibration only learns while the controller is “still” below this threshold (value × 0.0025641 / 100, written as half-float to embedded page register 0x98). Stock takes it from a Steam setting. This forces your value whenever the firmware applies that setting. Lower = calibration triggers less often during slow aiming (less “pull”) but bias drift is corrected less. experimental

Wireless poll rate

—
How the Puck paces the link. Each connected slot runs a loop that waits on its event object for up to 99 ticks (≈3 ms) and then polls the controller once; the poll itself (radio + handing the report to USB) takes about 1 ms, which gives the stock ~240 reports/s. This patch shortens that wait at all its call sites and sets the slot HID endpoints from 2 ms to 1 ms (the 2 ms interval alone caps the link at 500 Hz). Sites are found by code structure (the timed waits on the same event-wait function that the loop also calls with K_FOREVER, and the 4-endpoint HID slot interfaces), not by fixed addresses, so other Puck versions work as long as that structure is unchanged; if it isn’t found the patcher refuses instead of guessing.

Measured (controller on sc26re 1k v5+, which builds ~1000 reports/s and always hands the Puck the newest): stock 240 · 1 ms 516 · 0.5 ms 680 · max 828 reports/s, link stable, haptics OK. The stock controller firmware gains little: it only produces ~250 distinct reports/s over the Puck. With several controllers on one Puck the slots share the radio.

Flashing the Puck (sc26re flash.py, needs pip install hidapi pyserial): python flash.py list → python flash.py enter-bl --serial <puck> → python flash.py bl-flash --firmware <file> --serial <puck>. Keep the stock file to flash back. Steam keeps the patched Puck because the firmware’s build stamp is unchanged.
What changed vs v1 & how it works
Re-patching. Every site is matched in both its stock and patched form, so you can drop a patched file, inspect it, and change or revert options. Reverting writes the known stock encodings of the IBEX_FW_6ACFF323 family.

v1 fixes. Tick rate is 32768 Hz (v1 assumed 16384, so its loop ran 2× faster than shown). The “priority 14” fix ties with the input thread rather than going below it. Gyro 1000 / accel 500 in v1 never took effect because of the driver restore bug; v2 patches the restore, and v2.1 also fixes the high-accuracy ODR setters so HA01 really runs at 1000/500 Hz.

New sites. HA ODR setters (2 × 78 B in place), USB report k_timer (1 byte), driver ODR restore (2 × ldrb → movs), capsense channel B, deflection threshold, gyro-calibration threshold, interval attribute.

Safety. Each site must match exactly once, or that option is refused or skipped. The output is re-inspected after patching. Flashing is reversible, so keep your stock file.

Measure it. Use the companion SC2 Report Meter (WebHID) to check the real report rate, jitter and gyro sample rate.
